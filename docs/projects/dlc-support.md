# Data Backend Overhaul (DLC Support) — Master Plan & "Ultimate Extractor" Architecture

> **Scope**: This is bigger than DLC. It is a **complete overhaul of the site's data backend.** Today every data file (`apps/web/src/lib/elden-ring-raw-db/*.ts`, the Rust `db/*.rs`, `map-db.ts`, and `assets/erdb/`) is hand-/erdb-generated and frozen at game v1.10. We replace all of it with **one repeatable command you point at your Elden Ring install dir** that re-exports _everything_ the site needs — items, equipment, event flags (graces/bosses), regions, map markers, and map images — making the extractor the single source of truth. DLC (Shadow of the Erdtree) is the forcing function and first payoff; future patches become a one-command refresh.

> **Status (2026-06-02)**: Research + tooling survey complete; reference repos cloned (incl. **SoulsFormatsNEXT** + **UXM-Selective-Unpack** on Windows). **Decided:** extractor = **Effect-TS on Bun** (§5); **runs on native Windows** so `bun:ffi` can load the game's Oodle DLL (§1). **Phase 0 scaffold done.** **Phase 1 in progress, two gates PASSED on the real install:** (a) **Oodle** — `bun:ffi` loads `oo2core_6_win64.dll` (v6, not v9) and does a Kraken roundtrip; impl in `src/external/oodle.ts`. (b) **dvdbnd unpack** — the game files are inside encrypted **BHD5/BDT** archives (no loose `msg/`/`menu/`/`map/`), so we built a full **UXM-parity unpacker** in TS (`src/archive/dvdbnd.ts` + `crypto/rsa.ts`, `formats/bhd5.ts`, vendored keys/dictionary): RSA-decrypt `.bhd` → parse BHD5 → hash-match → AES-128-ECB → `.bdt` slice. Verified by extracting real `item.msgbnd.dcx`. Idempotent (skip-if-exists), `--clean` re-extracts; full unpack run = 130,781 files. (c) **DCX** — `src/formats/dcx.ts` decompresses `DCX_KRAK`(Oodle)/`DCX_ZSTD`/`DCX_DFLT`(zlib); verified `item.msgbnd.dcx` → BND4 (note: DCX headers are **big-endian**, unlike BHD5). **Update:** Phase 1 is complete (FMG names, PARAM stats via vendored Paramdex, MSB markers, grace+boss flags, boss names, image extraction, codegen → `@elden-ring-compass/data`). **Phase 3 (own the save parser) is also done** — ER-Save-Lib compiled to WASM + integrated (`wasm-save-parser-rewrite.md`). **Next:** migrate `apps/web` to consume `@elden-ring-compass/data` (task #7) and the legacy-data teardown (`client-side-db.md`); MSB marker calibration + ItemLotParam placements remain for the map.

## 1. TL;DR — what we learned

- The site's existing `apps/web/src/assets/erdb/` (1.7 GB of icons + `map/lod_0.jpeg`) was generated by **[erdb](https://github.com/EldenRingDatabase/erdb)** (Python), which stalled at game v1.10 (pre-DLC). We already have an erdb-shaped pipeline; it just stopped.
- Map markers are placed by an **affine transform from game world (x,y) coordinates** (`apps/web/src/components/sections/interactive-map.tsx:331-344`). Those coordinates were originally **scraped from a website**. To pull them from game files we must parse **MSB** (map-studio binary) entity positions.
- **DLC item names + IDs** are cleanly available (clean base param IDs) from **[ER-Save-Lib](https://github.com/ClayAmore/ER-Save-Lib)** — the _new_ lib ClayAmore built with vswarte & Nordgaren. The old ER-Save-Editor db is stale (byte-identical to ours, no DLC).
- **DLC boss/grace event flags** are NOT in any clean param. They live in **EMEVD** event scripts. Best programmatic source: **[soulstruct](https://github.com/Grimrukh/soulstruct)** (Python), which ships **116 decompiled DLC `m61` event scripts**. Pragmatic fallback: the **Grand Archives cheat table** (trivially parseable, 105 DLC graces + DLC boss flags already labeled).
- The binary-format ecosystem is dominated by **C#** (SoulsFormats / WitchyBND / Smithbox) and **Python** (soulstruct). **Rust** (ER-Save-Lib) covers regulation/params but not MSB/EMEVD/FMG/TPF. **TS/Bun** has no native FromSoft parsers — so a TS extractor means _porting_ parsers (which we want anyway, to own updates).
- **Two separate programs.** The **extractor** is a build-time tool (language = our choice → **Effect-TS on Bun**, see §5). The **save parser** is the runtime, in-browser **Rust → WASM** module and stays Rust. The language question is _only_ about the extractor.
- **DCX/Oodle handling.** `regulation.bin` is now **`DCX_ZSTD`** (trivial anywhere). Other game files (msg/tpf/msb/emevd) use **`DCX_KRAK` = Oodle**, decompressed via the game's own `oo2core_*_win64.dll` — which **ships in the install dir** we target — loaded from Bun with `bun:ffi`. **Decision: use the DLL, matching soulstruct and WitchyBND** (both load the same DLL). Consequence: the extractor **runs natively on Windows** (`bun:ffi` loads host-OS libs, and a Windows `.dll` can't be loaded from WSL/Linux). An open-source `ooz` → wasm Kraken decoder _would_ make it OS-portable, but we deliberately chose the DLL to stay aligned with the reference tools; ooz/wasm is parked as a future portability option.

## 2. The vision (one-command extractor)

```
   C:\Program Files (x86)\Steam\steamapps\common\ELDEN RING\Game\
   ├── regulation.bin            (encrypted: all params — items, equip, bonfires, worldmap)
   ├── msg/engus/*.msgbnd.dcx    (FMG text: names + descriptions, incl. *_dlc01)
   ├── menu/**/*.tpf.dcx         (icons + world map tile textures, incl. Land of Shadow)
   └── map/mapstudio/*.msb.dcx   (entity world coordinates — graces, bosses, items)
                    │
                    ▼
        ┌───────────────────────────┐
        │   er-extractor (1 command) │
        │   point at install dir      │
        └───────────────────────────┘
                    │
                    ▼
   apps/web/src/...                         packages/elden-ring-save-parser/src/db/
   ├── lib/elden-ring-raw-db/*.ts           ├── *.rs  (parser name/flag tables)
   ├── lib/map-db.ts (markers + coords)
   └── assets/erdb/{icons,map}/*            (icon atlases + Land of Shadow map image)
```

The extractor is the deliverable. DLC content then "falls out" of running it against a DLC-patched install. Same command keeps the site current on every future patch.

## 5. The decision: what language for the extractor

Reframed by two facts that dissolve most of the apparent tradeoff:

**(a) Two programs, not one.** The **save parser** (parses the user's uploaded save _in the browser_) is already **Rust → WASM** and _stays_ Rust — WASM is right for client-side parsing, and its format/offset knowledge is ported from ER-Save-Lib (see _Dependency robustness_ below). The **extractor** (build-time, points at the install dir, regenerates all data files) is a _separate_ program whose language is a free choice. **This decision is only about the extractor.**

**(b) Import vs port.** If we _import_ soulstruct, Python wins by default — that's where the MSB/EMEVD parsers live. But the self-update goal (see _Dependency robustness_) means we want to **own the format logic**, i.e. _port_ it. Once we're porting, the language is genuinely free and should be our preferred one.

→ **Recommendation: build the extractor in Effect-TS on Bun.**

- Matches the monorepo and the in-progress Effect-TS conversion; keeps the repo **bilingual** (Rust/WASM runtime + TS tooling) instead of adding Python as a third language.
- Effect's typed errors, `Schema`, and structured concurrency fit a multi-stage pipeline that emits validated artifacts and fans out cleanly.
- **Oodle handled via the game's DLL** (see §1): `regulation.bin` is plain zstd; the Oodle (`DCX_KRAK`) game files are decompressed by loading the game's own `oo2core_*_win64.dll` via `bun:ffi` — same approach as soulstruct/WitchyBND. **The extractor therefore runs on native Windows** (a Windows DLL can't be `dlopen`'d from WSL/Linux). `ooz`→wasm is a parked future option if OS-portability is ever wanted.
- We're porting parsers for ownership regardless; doing it in TS is no more _net_ effort than maintaining a Python fork, and it lands in our preferred stack.

**Honest cost.** We reimplement what SoulsFormats/soulstruct debugged over years. Easy ports (DCX, BND4, FMG, PARAM rows, TPF container) are bounded; **MSB and EMEVD are large** ports. Mitigation — go incremental:

- **v1**: Bun/Effect-TS owns orchestration + zstd/Oodle unpack + FMG + PARAM + TPF/DDS images + all joins + codegen. For the two hard parsers, _temporarily_ shell out to **WitchyBND** (MSB → XML) and use the **Grand Archives CT** overlay for boss flags.
- **v2+**: port MSB, then EMEVD, into TS — dropping WitchyBND and deriving boss flags from game files, reaching the fully-self-updating, zero-external-dependency ideal.

Gives the preferred language now and a clear path to the ideal, blocked on no other project's release cadence.

_(Python remains a fallback only if we'd rather import soulstruct than port MSB/EMEVD — trading the self-update ideal and language fit for less upfront parser work.)_

## 6. Pipeline stages (language-agnostic)

1. **Locate & unpack** — game files live in encrypted **BHD5/BDT** archives (`Data0-3`/`DLC`/`sd`). `src/archive/dvdbnd.ts` ports UXM's Selective Unpacker (RSA `.bhd` → BHD5 → AES → `.bdt`) to write loose files into the game dir; idempotent skip-if-exists + `--clean`. `regulation.bin` is loose (DCX_ZSTD) and read directly by the params stage.
2. **Params** — extract EquipParamWeapon/Protector/Goods/Accessory/Gem, BonfireWarpParam, WorldMapPoint → rows by id.
3. **Text (FMG)** — extract weapon/protector/goods/accessory/arts/place names + captions → id→string.
4. **Join** — params ⨝ text → item/equipment records (base + DLC together).
5. **Markers (MSB)** — parse m60/m61 MSBs → entity (x,y,z); map entity ids ↔ event flags ↔ names → `map-db` coordinates. Calibrate to the existing affine transform.
6. **Flags (EMEVD)** — derive grace + boss defeat flags (soulstruct) **or** apply curated CT overlay.
7. **Images** — extract DLC icon atlases + Land of Shadow map image (TPF→DDS→PNG/JPEG); produce `assets/erdb/map/*`.
8. **Codegen** — write `apps/web/src/lib/elden-ring-raw-db/*.ts`, `map-db.ts`, and `packages/.../src/db/*.rs` deterministically. Rebuild WASM.
9. **Verify** — diff against a real DLC save (we have one) — inventory item names resolve, discovered DLC graces/bosses toggle correctly, markers land in the right place.

Each stage is a module with typed inputs/outputs so stages can be swapped (e.g. CT overlay ↔ EMEVD) without rewrites.

## 7. Dependency robustness — what self-updates vs goes stale

The whole point of the extractor is that re-running it on a patched install refreshes the site **without waiting on any other project**. Whether that actually happens, per capability, hinges on one distinction:

- **Format parse** = "how to read a TPF/FMG/MSB/PARAM binary." Stable across patches (FromSoft changes _content_, almost never _file formats_) → **self-updates**.
- **Baked content / offsets** = hardcoded tables, decompiled scripts, param field defs, save offsets, AES key → **goes stale** on patch until someone updates them.

**Rule:** run _parsers_ against your install's binaries; never consume another repo's _checked-in data snapshot_. (soulstruct's 116 decompiled `.evs.py` files are a snapshot — the durable path is to run its EMEVD _reader_ on your install's binary EMEVD instead.)

| Target                         | Self-regenerates from install? | Leans on                                                         | Content patch           | Format/save revision                  |
| ------------------------------ | ------------------------------ | ---------------------------------------------------------------- | ----------------------- | ------------------------------------- |
| Item images (icons)            | ✅                             | TPF/DDS format                                                   | auto                    | ~never changes                        |
| Map images                     | ✅                             | TPF/DDS format                                                   | auto                    | ~never                                |
| Names (all)                    | ✅                             | FMG format                                                       | auto                    | ~never                                |
| Item/marker locations          | ✅ coords                      | MSB format + **our** join logic                                  | auto                    | ~never                                |
| Event flags — **graces**       | ✅                             | `BonfireWarpParam` + paramdef                                    | auto                    | paramdef drift (we vendor)            |
| Event flags — **boss defeats** | ◐                              | EMEVD reader + **EMEDF** defs + **our** heuristic                | auto for known patterns | new mechanic → EMEDF bump (we vendor) |
| **Save file parsing**          | ⚠️ **no**                      | save offsets + flag-bit formula + AES key (**all RE'd / baked**) | reads new flag ids fine | **save-format change needs RE**       |

**The one intrinsic dependency is save parsing.** The save's byte layout is _not described anywhere in the install dir_ — it exists only in the game's compiled save code. When FromSoft revises it (the DLC did), the only recovery is reverse-engineering by diffing saves — the "tricky, only the author could do it" work. ER-Save-Lib (ClayAmore + vswarte + Nordgaren) is the current encapsulation: offsets + `src/res/eventflag_bst.txt` (the flag-id → bit-offset mapping that _was_ the hard RE) + the hardcoded AES key. It reads current DLC saves but does **not** auto-update on a future save-format revision. This is rare, though: normal content patches don't move the save layout, and new DLC flag ids slot into the existing structure, so flag _reading_ keeps working.

**Strategy — own the format knowledge.** Treat the other repos as _sources to copy from_, not runtime deps we wait on:

1. **Vendor** Paramdex (paramdefs), EMEDF (event-instruction defs), and the AES key into our repo.
2. **Fold the save parser into the project**: port ER-Save-Lib's save-format + event-flag-bit logic into our existing Rust/WASM parser (today a stale copy of old ER-Save-Editor). Then _we_ own the save offsets and update them on a format revision — on our schedule.
3. **Log** every curated/derived boundary (esp. boss flags) so a patch never silently leaves data stale.

Result: images, names, locations, and graces are **fully self-updating and owned**; boss flags self-update except rare EMEDF drift we control; save parsing self-updates across content patches, and the one unavoidable manual step — RE a new save format after a _major_ patch — is **ours to do on our schedule**, not a blocker we wait on.

```
  regulation.bin                     # AES-encrypted BND4 of all params (incl. DLC)
  msg/engus/item.msgbnd.dcx          # FMGs: weapon/protector/goods/accessory/arts names+captions (+ _dlc01)
  msg/engus/menu.msgbnd.dcx          # place names, menu text (+ _dlc01/_dlc02 stubs)

  menu/71_maptile*.tpf.dcx (approx)  # world map tile textures (Lands Between m60 + Land of Shadow m61)
  map/mapstudio/m60_*_*.msb.dcx      # Lands Between map layouts (entity coords)
  map/mapstudio/m61_*_*.msb.dcx      # Land of Shadow (DLC) map layouts
```

(DLC is integrated into the _same_ base files — `regulation.bin` carries DLC params, `item.msgbnd` carries `_dlc01` FMGs — so a DLC-patched install needs no special DLC archive handling beyond reading those entries.)
